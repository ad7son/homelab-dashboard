# System Monitor 後端

## 1. 系統用途

透過採集器定期取得主機硬體資料來源。每輪採集結果先寫入 SQLite，再由 API 提供查詢，提供兩種查詢：

- **最新資訊**：目前的主機基本資訊與最近一次成功儲存的監測指標。
- **歷史資訊**：指定時間範圍的監測指標，必要時彙整為時間桶平均值。


## 2. 整體架構

```text
projects/system-monitor/backend/
├── src/
│   ├── __init__.py
│   ├── plugin.py          # 平台整合入口
│   ├── config.py          # 共用設定
│   ├── api/               # HTTP 查詢
│   ├── collector/         # 硬體採集與程序管理
│   └── database/          # SQLite 存取
├── tests/                 # 對應模組的測試
├── README.md
├── requirements.txt       # 執行依賴
├── requirements-dev.txt   # 開發工具
└── pyproject.toml         # 工具設定
```

| 模組 | 責任 |
|---|---|
| `plugin.py` | 掛載 API、管理採集器生命週期、宣告監測功能 |
| `api/` | 驗證查詢參數、安排歷史彙整粒度、建立 HTTP 回應 |
| `collector/` | 採集器。讀取硬體、安排採集、保存結果與觸發過期清理 |
| `database/` | 管理 SQLite 連線、資料表與 SQL 操作 |

API 與採集器分開執行，透過 SQLite 交換資料。採集器故障不會直接中止**查詢服務**，但最新資料會停止更新。共用設定集中於 [config.py](src/config.py)，兩個程序必須指向同一份資料庫。執行資料預設集中於儲存庫根目錄的
`data/system-monitor/`，與程式碼分開，整個 `data/` 不納入 Git。

## 3. 各模組架構

### 3.1 API：`api/`

```text
src/api/
├── __init__.py
├── router.py       # 組合兩個查詢路由
├── schemas.py      # HTTP 回應模型
└── routes/
    ├── __init__.py
    ├── overview.py # 最新資訊查詢
    └── history.py  # 歷史區間與彙整粒度
```

最新資訊查詢將**主機基本資訊**與**最新一筆指標**組合為回應，保留原始取樣時間。沒有基本資訊或監測紀錄時，不產生替代數值。

歷史查詢由路由決定時間視窗與彙整粒度，再交由 Repository 執行 SQL。
長區間在資料庫內彙整，避免將全部原始紀錄載入 API 程序後才計算。
平均值忽略缺值，全缺值仍為缺值，也不補造沒有紀錄的時間桶。

### 3.2 採集器：`collector/`

```text
src/collector/
├── __init__.py
├── __main__.py     # 子程序入口、停止訊號與父程序監聽
├── process.py      # 程序鎖、啟動、重試與回收
├── runner.py       # 採集排程、寫入與過期清理
├── host_reader.py  # 持有並組合各 Reader
└── readers/
    ├── __init__.py
    ├── cpu.py      # CPU 指標
    ├── memory.py   # 記憶體與 Swap
    ├── network.py  # 網路介面與流量
    ├── gpu.py      # GPU 資訊與使用率
    └── disk_io.py  # 磁碟讀寫速度
```

`HostReader` 持有同一組 Reader，保留 CPU、網路與磁碟的取樣基準。基本
資訊只在採集器啟動時讀取；動態資訊按排程持續採集。硬體或介面改變後，
需重啟採集器才能更新基本資訊與裝置選擇。

各項資訊依序讀取，不是同一瞬間的原子快照。單項讀取失敗不阻止其他
指標保存；無法取得的資料保留缺值，與有效零值區分。首次需要建立速率
基準的指標，也不以零假裝已有讀值。

`runner` 以固定起點間隔安排採集，超時就跳過錯過的排程點，不重疊、
不補採。過期清理只在完整清理間隔後執行，不在啟動時清理；永久保留時
跳過。清理計時不跨重啟保存，因此頻繁重啟可能使清理一直未執行。

### 3.3 資料庫：`database/`

```text
src/database/
├── __init__.py
├── connection.py  # 初始化、連線與交易
├── repository.py  # 基本資訊與監測指標的 SQL 操作
└── schema.sql     # 資料表定義
```

| 資料表 | 保存方式 | 設計目的 |
|---|---|---|
| `host_info` | 保留目前版本，採集器啟動時更新 | 避免每輪重複儲存基本資訊 |
| `host_metrics` | 每輪新增一筆，以取樣時間識別 | 保存可查詢與彙整的指標變化 |

兩張表不保存基本資訊的版本關聯，因此無法還原舊紀錄當時的硬體配置。
最新查詢組合目前基本資訊與最新指標，歷史查詢則只提供數值趨勢。
目前資料結構針對單一主機，多主機支援需另行設計資料關聯。

Repository 每次操作自行開關連線，寫入與刪除透過交易執行。SQLite 使用
WAL 支援查詢與採集並行；相同時間戳不覆蓋既有紀錄。保留政策由採集器
決定，Repository 只執行刪除；刪除後的空間供後續寫入重用，不自動縮檔。

資料表定義以 [schema.sql](src/database/schema.sql) 為準。目前沒有舊資料
遷移機制，修改建表 SQL 不會自動更新既有資料表。
